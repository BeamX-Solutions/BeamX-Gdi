# DB

## Overview

The data layer: Drizzle ORM 0.45 on Neon Postgres (Frankfurt) through the `neon-http` driver, the schema and its migrations, and the typed query layer every route, Server Action, `assistant/`, and `auth/` call into. Spec 0002 is the contract.

## Key files

| Path              | Owns                                                                                                                                                                                                                                            |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `client.ts`       | The one `db` instance (`drizzle(neon(env.DATABASE_URL))`)                                                                                                                                                                                       |
| `id.ts`           | `newId()`, UUID v7, the id helper for every app table and the AI SDK `generateId`                                                                                                                                                               |
| `errors.ts`       | `isUniqueViolation(e, constraint)` for mapping Postgres `23505` to typed errors; `billingAssertCode(e)` for the `billing_assert` code (`P0001`)                                                                                                 |
| `schema/`         | One file per domain (`chat.ts`, `runs.ts`, `usage.ts`, `credits.ts`, `payments.ts`, `profile.ts`, `consultations.ts`, `policies.ts`), re-exported from `schema/index.ts`; `auth.ts` is generated by Better Auth, never hand edit                |
| `migrations/`     | Generated SQL plus drizzle meta; never hand edit. Custom SQL (a function, not a table) goes in a migration made with `pnpm db:generate --custom`, like `0002_billing_assert.sql`                                                                |
| `queries/`        | The query layer: `conversations`, `messages`, `runs`, `reports`, `usage`, `users`, `credits` (plus the money statement builders in `credit-holds`), `payments`, `profile`, `consultations`, `policies`, `export` (with the pure `export-shape`) |
| `test/helpers.ts` | Integration test helpers: `guestTracker`, `runWithAnswers`, `completeFromAnswers`, `unwrap`, `fundRun`                                                                                                                                          |

## Commands

```bash
pnpm db:generate        # write a migration after any schema change, then commit it
pnpm db:migrate         # apply migrations (uses DATABASE_URL_UNPOOLED)
pnpm db:check           # migrations folder consistency only, NOT schema drift
pnpm test:integration   # *.int.test.ts against a real Neon branch
```

## Conventions

- Every user facing query takes the session `userId` and filters by it; another user's row returns a typed `not_found`, never data. Expected outcomes return `Result` (`@/lib/result`); only infrastructure failures throw.
- Keep each call to one round trip: multi step writes are one `db.batch` of independent statements (`neon-http` has no interactive transactions). Concurrency is enforced in SQL (row locks, compare and set, the partial unique index), not in app code.
- Writes that finish after a guest link (`onFinish`, the report step) get the owner from `conversations.ownerOf` or `runs.ownerOf`, never from the session captured when the stream started. Both are server only.
- Every new user owned table must be added to `users.linkGuest` and given a delete rule (cascade, or SET NULL for business records). `link.int.test.ts` reads every foreign key to `user.id` and fails on a table that is neither linked nor excluded.
- A new user owned table also joins `export.readAll`, the one batched, owner filtered read behind "Download my data" (spec 0017, AC-7), and `export-shape.ts`. Never select secrets or provider references there (the Paystack reference stays out).
- `policy_acceptance` (spec 0017) changes only through `queries/policies.ts`: `record` is idempotent (unique on user, policy and version), `newestVersions` reads both policies in one statement.
- Schema changes are additive only (spec 0002, AC-12): new tables, nullable columns, foreign keys, enum values. Anything else goes back through `/architect`.
- Timestamps use `mode: "string"`. Pass them back as the raw strings (for example `lastAnswerAt` to `runs.complete`); a JS `Date` drops the microseconds and breaks the answer fingerprint.
- `messages.append` upserts by message id only within the same chat and the same role; a reused id of another role or chat writes nothing and returns 0 (callers treat 0 as "not saved").
- Hand written SQL goes through Drizzle's `sql` template with bound parameters, never string concatenation.
- Money writes (spec 0004) go only through `queries/credits.ts` and the builders in `queries/credit-holds.ts`; each writes its ledger entry in the same batch. A failed money check inside a batch calls `billing_assert(ok, code)`, which raises `P0001` and rolls back the whole batch; map it back with `billingAssertCode`.
- A `payment` row changes only through `queries/payments.ts`. `markSucceeded` is one statement guarded by the status, the amount, the currency and the `purchase:<paymentId>` ledger key, so the webhook, the callback and the sweep can race and the credits are granted once. Nothing leaves `succeeded`, and a late success still grants a `failed` or `abandoned` payment. Payments outlive their user (`ON DELETE SET NULL`).
- A `consultation` changes state only through `queries/consultations.ts`: `book` (offered → booked) and `cancel` (booked → canceled) are single conditional updates, so Calendly's webhook retries move nothing twice. A partial unique index keeps one offer per chat (spec 0016).
- `reports.claim` and `reports.markReady` need an active credit hold on the run. Integration tests that claim a report call `fundRun` after starting the run.
- A `partial` report (spec 0013, a tool with `phasesPerCall: 1` between calls) is claimed again on the same attempt: `attempts` counts failed calls, not phases. `reports.status` returns the run's `scores` only while the report is not ready (a tool's preview).
- `business_profile` facts (spec 0012) change only through `queries/profile.ts`, whose single merge rule keeps the later `updatedAt` per key. `users.linkGuest` merges the guest profile into the account and deletes it (it is in `LINKED_TABLES` but merged, not moved). Facts from a completed run are written in the `runs.complete` batch, skipping answers whose `source` is `profile`.

## Testing

- Integration tests (`*.int.test.ts`) run against a throwaway Neon branch, never `production` or `dev`. CI creates and deletes one per PR. Locally, export the branch's `DATABASE_URL` and `DATABASE_URL_UNPOOLED` before running; exported vars win over `.env`.
- Each test file owns its users through `guestTracker()` and cleans up by deleting them (the cascade removes their rows), so files can share one branch.
- A folder filter such as `vitest run src/assistant` also picks up `*.int.test.ts`, which then run against the `DATABASE_URL` in `.env` (the dev branch). Add `--project unit` when running unit tests by folder.

## Gotchas

- A CHECK that ties a column with an `ON DELETE SET NULL` user FK to another column must still hold after the null, or deleting the user aborts (that is why `luna_credit_import` checks `claimed_by_user_id IS NULL OR claimed_at IS NOT NULL`, not "both or neither").
- `drizzle-kit check` never compares the schema to the migrations. CI catches drift with a separate step: `pnpm db:generate`, then fail if `src/db/migrations` changed.
