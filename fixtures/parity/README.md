# Parity fixtures

These files capture what the original standalone tools produce, so the tools rebuilt inside the workspace can be tested against them (spec 0001: parity with the originals is required). Feature #20 in the scope.

Everything here is **generated from the original source code**. Don't edit these files by hand; regenerate them instead (below).

## Where they come from

| Tool       | Original repo                         | Local folder             |
| ---------- | ------------------------------------- | ------------------------ |
| Stellar    | `chimaobi-ibeh/biv`                   | `../biv`                 |
| Beacon     | `BeamX-Solutions/beamx-scorecard`     | `../beamx-scorecard`     |
| Beacon Pro | `BeamX-Solutions/beamx-scorecard-v2`  | `../beamx-scorecard-v2`  |
| Luna       | `BeamX-Solutions/paid-marketing-plan` | `../paid-marketing-plan` |

Each JSON file records the exact commit it was generated from under `source`, and whether that checkout had uncommitted changes.

## How they were made

The generators only **read** the original repos. They copy the pure code (questions, scoring, rule based advice, prompt builders) into a temporary folder and run the copies. Nothing touches the live tools, their databases, email, or any AI service, and no real client data is used: every answer set is chosen or generated by the script, with placeholder contact details (`Ada Test`, `ada@example.com`).

Regenerate (from the repo root, with the four repos cloned beside this one):

```bash
node scripts/parity/generate-ts-tools.mjs --stellar ../biv --luna ../paid-marketing-plan
python scripts/parity/generate_beacon.py ../beamx-scorecard ../beamx-scorecard-v2
```

Random cases use a fixed seed, so a rerun against the same commits gives the same files. A diff after regenerating means the original tool changed.

## What is in each folder

### `stellar/`

- `questions.json`: the 10 questions, options with `isPositive`, which answers trigger a follow up, and the minimum text length that counts as positive.
- `scoring.json`: 75 cases (15 named, 60 random). Each holds the responses and the original `calculateScore` and `calculateDimensionScores` output.
- `ai-output-schema.json`: the JSON schema the AI analysis must return, and the model it used.

### `beacon/` (Beacon and Beacon Pro)

- `questions.json`: every field in form order, its exact option strings, and the score map behind each scored question.
- `scoring.json`: 200 random cases with Beacon's full scoring output (total, readiness, the five categories with grades and insights, flags).
- `reports.json`: 34 named cases covering every readiness band from both sides of each threshold, every pain point, and every industry. Each holds Beacon's rule based advisory (the text before its AI polish step) and the exact prompt Beacon Pro sends the model, plus Beacon Pro's system prompt once.

### `luna/`

- `questions.json`: the 9 marketing squares and all 50 questions (12 business context, 38 questionnaire).
- `example-plan.json`: the reference plan from the Luna repo (a test business), showing the shape of a full plan.
- `plan-shape.md`: the `Plan` type and the five generation phases.

## What parity means for each tool

| Tool       | Must match exactly                                                                                 | Not compared                                      |
| ---------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| Stellar    | score, level, totalPositive, title, summary, actionItems, timeframe, dimension scores              | AI analysis text (only its shape, via the schema) |
| Beacon     | total, readiness level, category scores, percentages, grades, insights, flags, rule based advisory | AI polished wording                               |
| Beacon Pro | same scoring as Beacon (readiness level without the emoji)                                         | AI advisory text                                  |
| Luna       | question set and plan shape                                                                        | plan content (Luna has no scoring)                |

## Known differences on purpose

These are decisions, so a parity test should expect them rather than fail on them.

1. **Stellar dimensions are matched by question id, not answer order.** The original fills dimension N from the Nth answer it receives. That works on the standalone form, which always sends answers in order, but breaks in chat, where questions can be skipped or answers stored out of order. The port looks each dimension up by question id. For responses in question order (every fixture here) the result is the same.
2. **Stellar dimension 8 is renamed** from "Motivation" to "Competitor Awareness", because question 8 asks about competitors. The fixtures keep the original name, so a test maps it.
3. **Beacon's AI step moves from OpenAI (`gpt-4-turbo`) to Claude.** Scores and the rule based advisory are unaffected; only the polished wording changes, and that is never compared.
4. **Beacon and Beacon Pro scoring is one engine.** The generator checks on every case that both originals score identically (apart from the readiness emoji) and fails if they ever drift apart.

## Notes for the port

- Beacon rounding: Python's `round()` rounds halves to even, while JavaScript usually rounds halves up. That can't matter here: every Beacon score is a multiple of 1/15, so it never lands exactly on a half. `beacon/scoring.json` records the check (`roundHalfUpWouldDiffer: 0`).
- Stellar's own repo has unit tests for its scoring (`tests/scoring.test.ts`) that are worth reading alongside these cases.
